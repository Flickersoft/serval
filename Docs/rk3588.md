# Orange Pi 5 (RK3588) deployment

The CameraModule's deployment target. The same code and the same models run on desktop linux-x64
and on linux-arm64 — there is no per-architecture branch in the audio path.

```bash
dotnet publish -r linux-arm64 --self-contained -c Release -o ./pi
```

Verified: `libsherpa-onnx-c-api.so`, `libonnxruntime.so`, `libllama.so`, `libmtmd.so`, and
the `camera-module` binary all publish as aarch64, with no x86 libraries and no OpenCV.

On the Pi:

```bash
sudo apt install libportaudio2     # required: only the managed PortAudioSharp.dll is bundled
./scripts/fetch-models.sh
./camera-module --selftest              # models load and transcribe
./camera-module --capture-test f.jpg    # camera works
```

Set `Audio.DeviceName` and `Output.DeleteAfterSync=true`, then install
`deploy/camera-module.service` for run-on-boot.

**No libicu needed.** The build sets `InvariantGlobalization`, so a fresh Debian/Armbian image
runs the self-contained binary without the ICU package it would otherwise demand at startup.

**`libportaudio2` needs no `-dev` package and no symlink.** The runtime package ships
`libportaudio.so.2`; a `DllImportResolver` in the app loads that versioned soname directly.

**Audio does not need the NPU.** SenseVoice int8 runs comfortably on the A76 cores. Measured on
an RK3588: `rtf ≈ 0.05` (≈20× real time). Watch `rtf=` in the logs; it must stay well below 1.0.

## Logs

The module writes **no log file**. Everything goes to stdout, which under systemd means the
journal — and journald already handles rotation and retention (`SystemMaxUse=` in
`journald.conf`). An app-written rolling file would add flash wear on the SD card for no gain, and
would have to be carved out of the unit's `ProtectSystem=strict` sandbox besides.

```bash
journalctl -u camera-module -f              # follow
journalctl -u camera-module --since -1h     # recent history
journalctl -u camera-module --since today > camera-module.log   # a file to hand off
```

Verbosity and JSON output are two `Environment=` lines in `deploy/camera-module.service` — see
[configuration.md](configuration.md#logging-both-hosts).

## Vision on the NPU

**Measured: 5.9s/image vs 48s on CPU** — vision runs **8× faster on the RK3588 NPU** than on its
CPU. Both paths use the same Qwen3-VL-2B model and produce equivalent descriptions; the runner is
chosen by `Vision.UseNpu`. The CPU path (`UseNpu=false`, the default, LLamaSharp) is the portable
fallback. The NPU path (`UseNpu=true`, `RkllmVisionRunner`) needs the RK3588-specific stack below.

This is also the reason the model is Qwen3-VL rather than Gemma 4, which RKLLM lists under
text-only models.

1. **A Rockchip BSP (vendor) kernel with the `rknpu` driver ≥ 0.9.8.** RKLLM talks to the NPU
   through Rockchip's proprietary driver, which ships only in the vendor kernel. A mainline
   kernel binds the NPU to the open `rocket` driver instead, which RKLLM cannot use. Check:
   `uname -r` shows `-vendor`/`-rockchip` (not `-current`), and `/sys/class/devfreq/*.npu`
   exists. Driver version: `sudo cat /sys/kernel/debug/rknpu/version`.
2. **The RKLLM runtime libs**, next to the `camera-module` binary: `librkllmrt.so` (1.2.3) and
   `librknnrt.so`. Both are closed Rockchip binaries — take them from the Qengineering
   `Qwen3-VL-2B-NPU` repo (`aarch64/library/`) or the `airockchip/rknn-llm` +
   `airockchip/rknn-toolkit2` releases. They are version-locked to the models.
3. **The pre-converted models** in `models/qwen3-vl-npu/`:
   `qwen3-vl-2b-instruct_w8a8_rk3588.rkllm` and `qwen3-vl-2b-vision_rk3588.rknn` (~3.2 GB),
   from the Qengineering repo's Sync.com links (browser download — the links serve an app, not
   a direct file, so `wget` cannot fetch them).
4. **Run with the lib path set** so `librkllmrt.so` can find `librknnrt.so`:
   ```bash
   LD_LIBRARY_PATH=$PWD CameraModule__Vision__Enabled=true CameraModule__Vision__UseNpu=true \
     ./camera-module --describe frame.jpg      # ~6s, prints the description
   ```
   `deploy/camera-module.service` sets the same environment for the service.

Vision never blocks audio either way — the cost is latency on the `vision` field
(`vision_age_seconds` records it), not lost transcripts. If even the NPU is too slow for the
scene cadence, lower `Vision.Width`/`Height` first.

**Multi-frame vision does not work on the NPU.** The CPU path shows the model several consecutive
frames so it can describe movement; the RKLLM path cannot, because its image-embedding buffer is
sized for a single image. An RK3588 with `UseNpu` therefore describes stills. Worth revisiting if
RKLLM grows multi-image multimodal input.

**Object detection is server-only.** The module gates vision on `CameraModule:Motion` and nothing
else — no `IObjectDetector` is constructed here, and `CameraModule:Detection` exists solely for the
`--detect` and `--replay-gates` diagnostics, which are on the module because calibrating a camera
happens at the camera whichever host will eventually do the detecting. Running it here is not
blocked by anything in principle: the RKNN C API surface in `RknnInterop.cs` is already what a
YOLO-on-NPU implementation would need, and `Letterboxed` already produces the packed NHWC uint8
buffer that API takes. It is simply not built, and a half-working CPU detector competing with the
VLM for the same four cores would be worse than the motion gate it replaced.

## Conversation audio on tmpfs

Only relevant with `Speaker.Enabled`. The writes themselves are already flash-friendly — a 64 KiB
`FileStream` buffer and no per-window flush means one write every ~2s, not a stream of tiny ones.
The cost is volume: `ConversationTracker` tees *continuous* audio, silence included, so an open
conversation writes ~115 MB/hour and the file is deleted once diarized. That write-and-delete churn
is what wears SD/eMMC.

No code change needed — `Speaker.ConversationAudioDirectory` already points wherever you like, and
the systemd unit carries a commented-out `/run` (tmpfs) variant. It is off by default because it
trades away crash recovery: `DiarizationWorker` rescues conversations whose audio outlived the
process, and tmpfs does not survive a power cut. Budget ~58 MB per camera scope at the 30-minute cap.
